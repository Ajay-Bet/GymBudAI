### Connection strings

The backend reads one SQLAlchemy URL from `DATABASE_URL` (contract: "Database configuration" in `docs/sprints/sprint-5-STATUS.md`).

- **Cloud Run (built-in Unix socket)**, deployed with `--add-cloudsql-instances=PROJECT:REGION:INSTANCE` and `--service-account=gymbud-api-staging@PROJECT.iam.gserviceaccount.com`:
  `postgresql+psycopg://USER:PASSWORD@/DB?host=/cloudsql/PROJECT:REGION:INSTANCE`
  libpq/psycopg appends `/.s.PGSQL.5432` to the socket directory itself. The full socket path must stay under 108 characters. Supply it with `--set-secrets=DATABASE_URL=gymbud-staging-database-url:latest`. Cloud Run deployment itself is Sprint 12; nothing here deploys a service.
- **Local machine via Cloud SQL Auth Proxy** on port 5433 (5432 is the local Homebrew PostgreSQL):
  `postgresql+psycopg://gymbud:PASSWORD@127.0.0.1:5433/gymbud_staging_test`

### Cloud SQL Auth Proxy (local access)

Pin **v2.26.0** (latest listed in the docs on 2026-10-04; re-check before use):

```sh
# macOS Apple silicon (Linux amd64: cloud-sql-proxy.linux.amd64)
curl -fLo cloud-sql-proxy https://storage.googleapis.com/cloud-sql-connectors/cloud-sql-proxy/v2.26.0/cloud-sql-proxy.darwin.arm64
chmod +x cloud-sql-proxy
gcloud auth application-default login          # your account needs roles/cloudsql.client
./cloud-sql-proxy --port 5433 PROJECT:REGION:INSTANCE
```

Keep the binary out of Git. The `--port` option syntax is from the v2 proxy; confirm with `./cloud-sql-proxy --help`.

## Connection budget

Each API process opens at most `DB_POOL_SIZE` 5 + `DB_MAX_OVERFLOW` 2 = **7** connections.

```
Cloud Run max instances × 7  +  other clients  ≤  max_connections − reserved
```

| Tier | Default `max_connections` (verify in the instance's flags) | Reserved (superuser/maintenance, assume) | Usable |
|---|---|---|---|
| `db-f1-micro` | 25 | 3 | 22 |
| `db-g1-small` | 50 | 3 | 47 |

Proposed for staging on `db-f1-micro`: Cloud Run `--max-instances=2` → 14, plus one local integration-test run through the proxy (pytest process pool 7 + Alembic 1 = 8) → **22 ≤ 22**. That is exactly at the limit, so run integration tests only while Cloud Run is scaled down, or move to `db-g1-small`, or lower the pool for tests. Re-check this whenever max instances, pool size or tier changes.

## Cost controls

- Budget alert on the staging project (script creates one if `BILLING_ACCOUNT` and `BUDGET_USD` are set). **Budget alerts notify; they do not cap spending.**
- Shared-core zonal instance, 10 GB storage. Stop the instance when not needed (`gcloud sql instances patch INSTANCE --activation-policy=NEVER`, verify before running); storage and backups are still billed.
- Deleting the instance needs deletion protection removed first, deletes its automated backups, and is irreversible.

## Staging migration and integration test runbook

Run from the repository root after provisioning. Use the dedicated test database, never `gymbud_staging`, for pytest.

1. Start the proxy in its own terminal: `./cloud-sql-proxy --port 5433 PROJECT:REGION:INSTANCE`.
2. Point the backend at staging (password read from Secret Manager, not typed into files):
   ```sh
   cd backend && source .venv/bin/activate
   PW="$(gcloud secrets versions access latest --secret=gymbud-staging-db-password --project=PROJECT)"
   export TEST_DATABASE_URL="postgresql+psycopg://gymbud:${PW}@127.0.0.1:5433/gymbud_staging_test"
   export DATABASE_URL="$TEST_DATABASE_URL"
   ```
3. Migrations on the empty staging test database: `python -m alembic upgrade head`. Record the output.
4. Integration tests: `python -m pytest -q`. Record pass/fail counts.
5. Save-and-reload check: run the API against staging (`python -m uvicorn app.main:app --host 127.0.0.1 --port 8080`), register, save a set from the camera page, restart the API, sign in again and confirm the workout appears in history.
6. **SQL unavailable check:** with the API still running, stop the proxy (Ctrl+C). Call a database-backed endpoint, for example `curl -i -X POST http://127.0.0.1:8080/api/auth/login -H 'content-type: application/json' -d '{"email":"x@example.com","password":"x"}'`. Expect **HTTP 503** with `{"detail":{"code":"database-unavailable",...}}` within the pool timeout (10 s) and no stack trace in the body. `/health` should still answer 200 (it checks only the process). In the browser, a save should show **Failed** with **Retry**; restart the proxy and Retry should succeed without a duplicate set.
7. Clean up: `unset PW DATABASE_URL TEST_DATABASE_URL`; stop the proxy. Add the evidence (date, instance connection name, migration revision, test counts, 503 response) to `docs/sprints/sprint-5-STATUS.md`.

The same SQL-unavailable check can be run locally against Homebrew PostgreSQL (`brew services stop postgresql@18`), which does not need GCP.
